# Architecture — what each directory and package of the repo is

The reference map of the repo: read it before working in an area you do not know yet, or before
touching packaging and deployment. The root `AGENTS.md` keeps a one-line map and the rules every
task needs. A path written `docs/…` beside a package or an app means that zone's own `docs/`, as
everywhere in this repo ([lints.md](lints.md), which also holds the repo's own checks).

## The apps and the engine

`studio` holds the music/stage apps. Every app runs on the musician's device: k7 has no hosted
origin, so the audio side is one machine, the device's own, which is why this overview lives in the root `docs/` and not inside any one app. Two processes run on the
musician's machine — `apps/k7-daw-engine/k7-runtime` and `apps/k7-daw-engine/k7-supervisor` — either on their own, as the
command-line engine (`k7-supervisor --config <file>`), or inside an app: the desktop app (`apps/k7-daw-desktop`), through the k7 backend it runs, or the phone (`apps/k7-daw-android`, `apps/k7-daw-ios`).:

| dir | language | what it is |
|---|---|---|
| `apps/k7-daw-engine/k7-runtime` | C++ | The audio engine. Receives a compiled `ProjectDoc` over WebSocket, diffs it, plays audio, pushes transport and meter state back. **Never parses song files.** |
| `apps/k7-daw-engine/k7-supervisor` | C++ | The engine machine's **supervisor**: starts, adopts and watches the engine, keeps it listed at the studios it is connected to, holds the tunnel its own backend reaches the machine through, and runs the work the backend asks of the machine — a stem cut, a set list brought down, a file for the player (`docs/supervisor.md`). |
| `apps/k7-daw-engine/scripts` | Node | The scripts that build the engine and the supervisor and package what ships: the command-line engine's archive, and the desktop app's release files around the same binaries (`apps/k7-daw-engine/scripts/docs/buildEngine.md`). |
| `apps/k7-daw-android` | Kotlin (Gradle) | The engine on a PHONE: the same engine as a library the app loads, since JUCE's Android audio reaches Java, and the same supervisor as a program it runs, driven over stdio as k7's backend drives it under the desktop app. STANDALONE like the desktop app: it also runs k7's Rust front, bundled, so a phone opens its own studio. Foreground only (`apps/k7-daw-engine/k7-runtime/docs/android.md`). |
| `apps/k7-daw-ios` | Swift (Xcode) | The same on an IPHONE, part for part (and on an Apple-silicon Mac, as the iPad app: `ios.md`), with what iOS forbids answered: no app may run a program or start a process, so the engine AND the supervisor are frameworks run on threads of the app, k7's Rust front runs in the same process. The shell page and the page scripts are Android's own. Staged by `scripts/stage.mjs` before Xcode builds it (`apps/k7-daw-engine/k7-runtime/docs/ios.md`). |
| `apps/k7-daw-frontend` | TypeScript | The text-first DAW's page, and the only app that opens a project: React/Vite, with the Rust front of `apps/k7-daw-backend` that answers the session, the account's preferences, the file service, the engine registry and the built page; one process. Owns the timeline; shares the chains view. **Modules and chains are authored here**, against a project where the plugin a module names is actually LOADED, and written into a library folder of the device — a library is a plain folder, seeded from the `k7-core/` the app bundles and changed by an app update (`apps/k7-daw-frontend/packages/song/docs/sharedFolders.md`). A project is created from one of five **archetypes**: three named after the surface they open on — `arrangement` (a timeline), `mix` (two decks and a crossfade — `apps/k7-daw-frontend/packages/song/docs/setProject.md`), `video` (a timeline and a viewport) — and the two `live` ones, named after what they ARE: a rig you play THROUGH, with nothing arranged and no lane of any kind — an input, a fader, the master run, and in `live-video` a webcam feeding RENDER plus the one viewport a picture cannot do without (`apps/k7-daw-frontend/packages/song/docs/liveProject.md`) — and a song holds **sound and picture** alike: video lanes on the same timeline, whose ruler reads bars or seconds, and a `viewport` surface that composites them (`docs/picture.md`). What it draws beyond its panes, it draws because the project DECLARED it, in `surfaces/` (`docs/surfaces.md`). It opens the account's **playlists** as well — `_playlists/` at the workspace root, listing audio files of the workspace, a record each (`apps/k7-daw-frontend/docs/playlists.md`). A `turntables` surface NAMES one, and that is what the DJ desk's browser lists and what the machine pre-fetches before a gig. Beside those, `_references/` — the finished mixes you listen AGAINST, uploaded there and played by the BROWSER so a reference sounds over a live rig or a running arrangement without going near the engine (`apps/k7-daw-frontend/docs/references.md`). It owns the level above a project too: its **home page** — the ORIGIN with no project in the address — lists the device's workspaces, the projects inside them and the libraries (`apps/k7-daw-frontend/docs/projects.md`) — and its left sidebar carries the origin's USER MENU (`apps/k7-daw-frontend/docs/userMenu.md`). It runs on the device only, opened at the loopback address of its own front (the desktop app's `127.0.0.1:18789`) or in the app's own view; `docs.k7.rocks` serves its documentation alone (`apps/k7-daw-frontend/docs/docsSite.md`), and a project is addressed `/@local/<workspace>/<project>` — a folder on the machine that holds it, with `@banc` (the bench, a live rig seeded with a library chain) the only other openable address — plus `/external`, the menu of surfaces a second device drives, kept until the app's second-device rework (`apps/k7-daw-frontend/docs/external.md`). Opened ON one WORKSPACE otherwise, by an address rather than a picker — see `apps/k7-daw-frontend/packages/project-shell/docs/launch.md`. A workspace is one folder holding SEVERAL projects: the editor's tree is the whole of it and a ▶ on a project row is what hands that one to the engine (`apps/k7-daw-backend/docs/file-projects.md`). It is a git repository only once connected: a folder on the device that git moves between devices (`apps/k7-daw-backend/docs/files/git.md`), whose history between two commits is the capture's own log (`apps/k7-daw-backend/docs/files/history.md`). |
| `apps/k7-daw-backend` — the engine registry | Rust (routes) | The Rust front holds the engine registry (`apps/k7-daw-backend/docs/engine.md`) and the file hub over the device's WORKSPACES (`apps/k7-daw-backend/docs/files.md`), one file service for the one local account. A remote engine is not an app feature: the registry and tunnel code stay for the app's second-device rework (`docs/inventaire.md`). |
| `apps/k7-daw-backend` | Rust | k7's backend in Rust (`docs/rust-backend-plan.md`): `k7-front` listens where the backend listens, answers the file service, the engine registry and the last routes (`apps/k7-daw-backend/docs/front.md`); the install's token is the session (`apps/k7-daw-backend/docs/sessions.md`); `k7_front::embedded` runs the front inside a host's process — the desktop app links it, the phones reach it through `k7-embed`'s C library (`apps/k7-daw-backend/docs/embed.md`). `k7-js` reproduces the JavaScript number formats a file holds, natively (`apps/k7-daw-backend/docs/parity.md`); `k7-mediatek` is the media core: decode, analysis, envelopes, sidecars, transcodes and the picture's copies. |
| `apps/k7-daw-wasm` | Rust | The crates that build for the browser as WebAssembly: `k7-wasm` (the one module, the facade), `song`, `song-schema`, `song-edit`, `k7x`. The backend links `song`, `song-edit` and `k7x` by path; their TypeScript halves are packages of the frontend (below). |
| `apps/k7-daw-desktop` | Rust (Tauri) | **K7 DAW, k7 on a Windows, Linux or macOS computer**: a Tauri app with one window that runs k7's Rust front in its own process, on `http://127.0.0.1:18789` (the port in `apps/k7-daw-backend/standalone.json`, the table the phone uses too). The front answers the account's files itself and runs the machine's supervisor over stdio, on `~/.k7` and 8765, the same engine the command-line one would be (`apps/k7-daw-backend/docs/local.md`). Its window shows k7 at that address, and the desktop app's "Open in Browser" opens the same page in the person's browser; everything it needs is on the machine, so it works offline. Built locally on each OS (a `.dmg` on a Mac), and downloaded from the GitHub release page, with no updater of its own (`apps/k7-daw-desktop/docs/app.md`). The engine is the machine's own. |
## The shared packages

`apps/k7-daw-frontend/packages/` is **studio's own shared tier**. All are `@studio/*` and are consumed
as **raw TypeScript source**: no build step, imported through `package.json`
`exports` subpaths, so a bare deep import fails on purpose.

| group | packages |
|---|---|
| the song | `k7-wasm` (the browser's one WebAssembly module: Rust behind a C ABI carrying JSON, the curves and the timecode of `song-schema` first; `apps/k7-daw-frontend/packages/song-schema/docs/wasmBoundary.md`), `k7x` (the TEXT every workspace file is written in: Strudel-looking, parsed and never evaluated, edited value by value so every other byte stays — `docs/language.md`, and the plan `docs/k7x-plan.md` at the root), `song-schema` (the FILE FORMAT and the value vocabulary around it — one zod schema and one reader/writer per kind of workspace file, plus `timecode`, `moduleTypes`, `playlist`, `stems`… Nothing in it touches `node:fs`, which is the whole point: **this is the half a browser may import**, and k7's frontend, `ui-editor`, `ui-module-builder`, `k7-plugins` (the desk) and `project-shell` depend on it INSTEAD of on `song`), `apps/k7-daw-wasm/song` (the compiler's Rust crate `song`, linked by the backend and built for the browser: the `Source` it reads through, its cache and the file readers so far; `apps/k7-daw-frontend/packages/song/docs/rustCompiler.md`), `song-edit` (CHANGING a project rather than compiling one — params, assets, events, material, time; the implementation is the Rust crate `apps/k7-daw-wasm/song-edit`, run over WebAssembly in the verbs' Worker and over `__host.edit` in QuickJS, and the TypeScript is stubs and callback glue — `apps/k7-daw-frontend/packages/k7-wasm/docs/edit.md`; every write goes through a k7x document that changes the value and nothing else, so a knob drag stays a one-line diff), `song` (the READ side of a folder of k7x files — the loader, the module vocabulary, the lanes and the graph; the compile into the `ProjectDoc` is the Rust crate; a project is one of three SHAPES, `docs/setProject.md`; it also owns the WORKSPACE's shape around a project — the shared folders, the account's libraries and their third family `assemblies/`, and the `assemblies/` a project draws its nodes as BOXES with, `docs/assemblies.md`, and `_playlists/`, `docs/playlists.md`), `song-video` (the SAME folder → `VideoProjectDoc` for its picture — the video document model, the lane and chain compile, the shaders; `apps/k7-daw-frontend/packages/song-video/docs/picture.md`. Split out because a song's sound compiles without any of it; what stays in `song` is `videoOutputs.ts`, which edits the GRAPH rather than the picture, and `isVideoProject`, a folder probe `surfaces.ts` needs — the two edges that would otherwise make this a cycle), `song-strudel` (the Strudel side of a pattern lane — the hap → event mapping and the API the ENGINE runs, bundled into `apps/k7-daw-engine/k7-runtime` and tested here under Node; nothing imports it at run time, since the engine plays every pattern lane, `apps/k7-daw-engine/k7-runtime/docs/patternPlugin.md`), `commands` (one verb list for every surface — the dispatch and the document edits), `audio-probe` (MEASURING decoded audio: the trim gate and the envelope + beat grid. No `node:`, so a BROWSER may have it — k7's clip panel needs no node package for 69 lines of arithmetic), `audio-analysis` (no TypeScript: the Rust measure, decoders and encoders, the crate `apps/k7-daw-backend/packages/waveform`, built to the WebAssembly module `waveform.wasm` that the Rust front embeds for the `{file}.cache` sidecar, a file's true peak and the re-encodes; `docs/analysis.md`, `docs/transcode.md`), `take-render` (audio a song PRODUCES: the local render through the engine binary, a material consolidated, a wav's length), `video-prep` (what a probed video needs for the PICTURE — nothing, a remux, an optimized copy or a proxy; the probe and the copies are the Rust verb host's — `apps/k7-daw-frontend/packages/song-video/docs/media.md`), `audio-passes` (the offline passes a chain runs — process, peak, cold; the RUNNING is handed in by the host, `docs/processChain.md`), `translator` (`.dawproject` import) |
| the engine | `engine-protocol` (the wire, mirrored in C++), `engine-client` (Node), `engine-browser` (browser + React store; its `access` subpath is the ONE way an app reaches an engine — routes, probe, policy, lease, bound to that service's prefix), `engine-registry` (the internal seam's client and gate, through which the TypeScript reaches the Rust front's registry and tunnel hub, `docs/internalSeam.md`), `engine-tunnel` (the way IN: the supervisor dials the server that lists it — the hub is the Rust front's, the machine's agent in `apps/k7-daw-engine/k7-supervisor` with `agent.ts` its TypeScript reference — the server reaches the engine through that socket however far apart they are, a server-owned project plays from a local copy, and a browser gets a WebRTC path straight to the engine's machine — `docs/tunnel.md`, `docs/rtc.md`) |
| the disk | (every file operation is the Rust front's, `apps/k7-daw-backend/docs/service.md`: the front is the only backend, and an engine's machine has none: an engine is shared by the accounts that play on it, and what the server needs of that machine — a stem cut, a set list copied, a file brought down — is a job its supervisor runs over the tunnel, `apps/k7-daw-frontend/packages/engine-tunnel/docs/jobs.md`; the hub that keeps each account's workspaces under `$STUDIO_FILES_ROOT` is the front's too, `apps/k7-daw-backend/docs/files.md`), `user-prefs` |
| the views | `project-shell` (what an app needs BEFORE it can draw: the launch parameters, the file API's transport, the address → workspace resolution, the gate, and when a session goes to sleep, `docs/idle.md`), `ui-chains` + `ui-chains-react` (the chains graph — **k7 is the only host**, `docs/inventaire.md` §6), `ui-editor` (k7x + note grids, and the autosave every text pane runs on, `docs/autosave.md`), `ui-eyes` (WebGL video — k7's `viewport` surface), `ui-timeline` (what an arrangement surface needs whatever its unit is: wheel zoom, middle-drag pan, a ruler's tick chooser, the lane geometry — k7's ruler reads bars OR seconds, since one grid draws a song and its picture), `ui-waveform`, `ui-module-builder` (k7; the panel's rules and AI organize's check are `panel-rules`, React-free so k7's backend imports them without the builder), `ui-mini-player` (the transport BAR at the bottom of an app — play/pause, a scrubber, a close, and no transport of its own: k7's reference tracks mount the same row, `docs/miniPlayer.md`), and what the editor records with: `recorder` (a take's format, its live value, the metronome, a WebM's duration, `docs/recorder.md`); the DJ desk lives in `k7-plugins` (the sdk row below) |
| the types | `web-protocol`, `graph-model` (split out so drawing a graph doesn't drag in auth), `http-client` (the browser's side of a call to a studio service: a refusal's sentence and status, a time budget, an upload that reports its progress — k7's editor and home page share it, `docs/httpClient.md`) |
| the sdk | `k7-sdk` (the `K7Plugin` contract and the installers — a plugin is a set of commands, a surface, a set of modules, `docs/sdk.md`), `k7-plugins` (k7's builtin plugins and the two composition lists: the server half is `src/server.ts`, the shell registers the browser half into its pane ring — and it ABSORBED the DJ desk: `src/turntables/` is the desk's whole code, `docs/turntables/` its rationale, `scripts/turntables/` the harness that measures a GESTURE against a running engine — `put-on.ts`, what it costs to put a record on a deck that already holds one; `src/video/` is the viewport's, on the same pattern) |

Every package is private to this tree: k7 is the only consumer, and nothing is published by version.

## Production

**The apps run on devices.** k7 is K7 DAW (Windows, Linux, macOS), the Android app, and the iOS app: each carries its own front, file service, engine registry and engine, and moves workspaces by git (and iCloud keys on Apple devices). There is no hosted app, no account on a server and no server to pair with.

**`k7.rocks` is a static site.** GitHub Pages serves the front page and the documentation at `k7.rocks/docs`, built from this repository by `.github/workflows/pages.yml`; no server runs. Mobile apps come from the stores, desktop builds from the GitHub release page, and no app updates itself (`docs/site.md`). `docs/versioning.md` is the page on versions.

## `k7-core/`

`k7-core/` is a plain folder of this repository: the `@k7-core` modules library, the SEED every app bundles and copies a library folder from. It is here so
a module and the code it relies on change together, in one commit. It is a PUBLISHED version: its
`library.k7x` says which, and **a change to its content raises that `version`** in the same commit —
a version already installed is never rewritten, so an unchanged number reaches no machine
(`docs/library-versions-plan.md`). Its binaries (IRs, amp models,
presets) are ordinary tracked files; a path in it stays short, since a Windows checkout refuses one
past 260 characters.
